## 1. Introducción

El presente documento describe el proceso de integración y desarrollo de los módulos que componen el sistema web **Divina Providencia**.

La solución fue desarrollada bajo una arquitectura cliente-servidor, integrando una aplicación frontend construida con React y Vite, una API REST desarrollada con Spring Boot y una base de datos MySQL.

Durante el desarrollo se integraron los módulos principales de autenticación de usuarios, gestión de alojamientos y gestión de reservas. También se implementaron pruebas unitarias, control de versiones con Git, compilación de los componentes del sistema y mecanismos básicos de seguridad.

El propósito de esta evidencia es documentar la forma en que los diferentes componentes de la aplicación fueron desarrollados, integrados y verificados de acuerdo con los requerimientos definidos para el proyecto.


## 2. Objetivos y alcance del sistema

### 2.1 Objetivo general

Desarrollar e integrar los módulos principales del sistema web **Divina Providencia**, aplicando una arquitectura cliente-servidor que permita la comunicación entre el frontend, el backend y la base de datos, garantizando el funcionamiento de los procesos de autenticación, consulta de alojamientos y gestión de reservas.

### 2.2 Objetivos específicos

- Integrar una interfaz web desarrollada con React y Vite con una API REST construida con Spring Boot.
- Implementar el módulo de autenticación para el registro y validación de usuarios.
- Implementar el módulo de alojamientos para consultar y administrar la información disponible.
- Implementar el módulo de reservas para registrar y gestionar solicitudes asociadas a los alojamientos.
- Utilizar MySQL como sistema de gestión de base de datos para almacenar la información persistente de la aplicación.
- Aplicar una organización modular del código mediante componentes, servicios, controladores, modelos y repositorios.
- Incorporar mecanismos básicos de seguridad para el tratamiento de las credenciales de acceso.
- Implementar pruebas unitarias para verificar el comportamiento de los principales servicios del sistema.
- Utilizar Git como herramienta de control de versiones durante el desarrollo e integración del proyecto.
- Generar las versiones compiladas del frontend y del backend para comprobar que los módulos pueden ser preparados para un entorno de producción.

### 2.3 Alcance del sistema

El sistema **Divina Providencia** permite realizar las operaciones principales relacionadas con la consulta de alojamientos y la creación de reservas mediante una aplicación web integrada.

El alcance desarrollado para esta evidencia comprende los siguientes módulos:

**Autenticación:** permite registrar usuarios y validar sus credenciales de acceso. Las contraseñas son procesadas mediante un mecanismo de codificación antes de ser almacenadas.

**Alojamientos:** permite consultar los alojamientos registrados, visualizar sus características principales y utilizar esta información desde el frontend para seleccionar una opción de hospedaje.

**Reservas:** permite registrar reservas asociadas a un alojamiento existente, incluyendo información del huésped, fechas de entrada y salida, número de personas y estado de la reserva.

La solución se encuentra dividida en tres componentes principales:

- **Frontend:** aplicación desarrollada con React y Vite encargada de la interfaz y de la interacción con el usuario.
- **Backend:** API REST desarrollada con Spring Boot encargada de procesar las reglas de negocio y exponer los servicios del sistema.
- **Base de datos:** MySQL, utilizada para almacenar de manera persistente la información de usuarios, alojamientos y reservas.

La integración entre el frontend y el backend se realiza mediante peticiones HTTP a los endpoints de la API REST.

## 3. Arquitectura, capas y tecnologías utilizadas

### 3.1 Arquitectura general del sistema

El sistema **Divina Providencia** utiliza una arquitectura cliente-servidor, en la cual la interfaz de usuario y la lógica del servidor se encuentran separadas.

La aplicación se divide principalmente en tres partes:

```text
Usuario
   ↓
Frontend - React / Vite
   ↓
API REST - Spring Boot
   ↓
Base de datos - MySQL
```

El usuario interactúa con la aplicación desde el frontend. React envía solicitudes HTTP al backend, y Spring Boot procesa dichas solicitudes, aplica las reglas de negocio y utiliza los repositorios para consultar o modificar la información almacenada en MySQL.

Esta separación permite organizar mejor el proyecto, mantener independientes las responsabilidades de cada componente y facilitar futuras modificaciones o ampliaciones del sistema.

### 3.2 Capas del frontend

El frontend fue desarrollado con **React** y se encuentra organizado principalmente en componentes visuales y servicios.

#### Capa de presentación

Está compuesta por los componentes de React encargados de mostrar la información y recibir las acciones del usuario.

Entre los componentes utilizados se encuentran:

- `Header`
- `HeroSection`
- `AuthSection`
- `AccommodationSection`
- `AccommodationCard`
- `ReservationForm`
- `Footer`

Estos componentes permiten dividir la interfaz en partes reutilizables y mantener una estructura organizada.

#### Capa de servicios

Esta capa centraliza la comunicación del frontend con la API REST.

Los principales servicios implementados son:

- `api.js`
- `authService.js`
- `accommodationService.js`
- `reservationService.js`

El archivo `api.js` define la dirección base de la API, mientras que los demás servicios contienen las funciones responsables de realizar peticiones HTTP para autenticación, alojamientos y reservas.

### 3.3 Capas del backend

El backend fue desarrollado con **Spring Boot** y sigue una organización por responsabilidades.

#### Controladores

Los controladores reciben las solicitudes HTTP provenientes del frontend y exponen los endpoints de la API REST.

Se implementaron los siguientes controladores:

- `AuthController`
- `AccommodationController`
- `ReservationController`

#### Servicios

La capa de servicios contiene la lógica de negocio del sistema.

Los principales servicios son:

- `AuthService`
- `AccommodationService`
- `ReservationService`

Esta capa actúa como intermediaria entre los controladores y los repositorios.

#### Repositorios

Los repositorios permiten realizar operaciones de persistencia utilizando Spring Data JPA.

Se implementaron:

- `UserRepository`
- `AccommodationRepository`
- `ReservationRepository`

Estos componentes permiten consultar, registrar, actualizar y eliminar información almacenada en la base de datos.

#### Modelos

Los modelos representan las principales entidades manejadas por la aplicación:

- `User`
- `Accommodation`
- `Reservation`

Estas clases representan la información que posteriormente es almacenada mediante JPA en la base de datos.

#### DTO

El proyecto también utiliza objetos de transferencia de datos para recibir y enviar información específica entre las capas.

Entre ellos se encuentran:

- `AuthRequest`
- `AuthResponse`
- `ReservationRequest`

Los DTO permiten controlar la información que se intercambia mediante la API sin exponer directamente toda la estructura interna de las entidades.

#### Configuración

El paquete de configuración contiene componentes utilizados de manera transversal por la aplicación.

Entre ellos se encuentran:

- `PasswordConfig`
- `WebConfig`

`PasswordConfig` permite configurar el mecanismo utilizado para codificar las contraseñas.

`WebConfig` configura CORS para permitir la comunicación entre el frontend y el backend durante el desarrollo.

### 3.4 Tecnologías y herramientas utilizadas

Para el desarrollo e integración del sistema se utilizaron las siguientes tecnologías:

- **HTML5:** estructura de la interfaz web.
- **CSS3:** estilos y presentación visual.
- **JavaScript:** lógica del frontend.
- **React:** construcción de componentes reutilizables para la interfaz.
- **Vite:** entorno de desarrollo y compilación del frontend.
- **Java 21:** lenguaje utilizado para desarrollar el backend.
- **Spring Boot:** framework utilizado para construir la API REST.
- **Spring Web:** implementación de controladores y servicios HTTP.
- **Spring Data JPA:** acceso y persistencia de información en base de datos.
- **MySQL:** sistema gestor de base de datos.
- **Maven:** gestión de dependencias y compilación del backend.
- **JUnit:** ejecución de pruebas unitarias.
- **Mockito:** simulación de dependencias durante las pruebas unitarias.
- **Git:** control de versiones del proyecto.
- **Visual Studio Code:** entorno de desarrollo utilizado durante la integración.

### 3.5 Comunicación entre componentes

La comunicación entre el frontend y el backend se realiza mediante solicitudes HTTP utilizando una API REST.

Por ejemplo, para consultar los alojamientos, el frontend realiza una solicitud al backend:

```text
GET /api/accommodations
```

Para registrar una reserva se utiliza:

```text
POST /api/reservations
```

Y para las operaciones de autenticación se utilizan endpoints como:

```text
POST /api/auth/register
POST /api/auth/login
```

El backend recibe estas solicitudes, ejecuta la lógica correspondiente y devuelve una respuesta que posteriormente es procesada por React.

Durante el entorno de desarrollo, la API se ejecuta en el puerto `8082` y el frontend de Vite en el puerto `5173`.

## 4. Módulos, casos de uso e historias de usuario

### 4.1 Módulos principales del sistema

El sistema **Divina Providencia** se encuentra organizado en tres módulos funcionales principales:

#### Módulo de autenticación

Este módulo permite registrar usuarios y validar sus credenciales antes de permitir el acceso a determinadas funcionalidades del sistema.

Sus principales responsabilidades son:

- Registrar nuevos usuarios.
- Verificar si un nombre de usuario ya existe.
- Codificar las contraseñas antes de almacenarlas.
- Validar las credenciales ingresadas durante el inicio de sesión.
- Informar si la autenticación fue exitosa o incorrecta.

#### Módulo de alojamientos

Este módulo administra la información relacionada con las opciones de alojamiento disponibles.

Sus principales responsabilidades son:

- Consultar todos los alojamientos.
- Consultar un alojamiento por su identificador.
- Consultar alojamientos disponibles.
- Registrar nuevos alojamientos.
- Actualizar alojamientos existentes.
- Eliminar alojamientos.
- Mostrar los alojamientos disponibles en la interfaz web.

#### Módulo de reservas

Este módulo permite registrar y gestionar las reservas realizadas sobre los alojamientos existentes.

Sus principales responsabilidades son:

- Consultar todas las reservas.
- Consultar una reserva por su identificador.
- Consultar reservas por estado.
- Consultar reservas asociadas a un alojamiento.
- Crear nuevas reservas.
- Actualizar reservas existentes.
- Eliminar reservas.
- Validar que el alojamiento seleccionado exista antes de registrar o actualizar una reserva.

### 4.2 Actores del sistema

Para el alcance desarrollado se identifican los siguientes actores principales:

**Usuario:** persona que interactúa con la aplicación web para registrarse, iniciar sesión, consultar alojamientos y realizar una reserva.

**Administrador del sistema:** actor responsable de gestionar la información disponible en el backend, incluyendo alojamientos y reservas mediante las operaciones proporcionadas por la API.

### 4.3 Casos de uso principales

#### CU-01 Registrar usuario

**Actor:** Usuario.

**Descripción:** permite crear una cuenta mediante un nombre de usuario y una contraseña.

**Flujo principal:**

1. El usuario ingresa sus credenciales.
2. El frontend envía la solicitud al backend.
3. El sistema verifica si el usuario ya existe.
4. La contraseña es codificada.
5. El usuario es almacenado en la base de datos.
6. El sistema informa que el registro fue realizado correctamente.

#### CU-02 Iniciar sesión

**Actor:** Usuario.

**Descripción:** permite comprobar las credenciales de un usuario registrado.

**Flujo principal:**

1. El usuario ingresa su nombre de usuario y contraseña.
2. El frontend envía las credenciales a la API.
3. El backend busca el usuario registrado.
4. El sistema compara la contraseña ingresada con la contraseña codificada almacenada.
5. El sistema devuelve el resultado de la autenticación.

#### CU-03 Consultar alojamientos

**Actor:** Usuario.

**Descripción:** permite consultar las opciones de alojamiento registradas en el sistema.

**Flujo principal:**

1. El usuario accede a la aplicación.
2. El frontend solicita los alojamientos a la API REST.
3. El backend consulta la información almacenada.
4. La API devuelve los alojamientos disponibles.
5. React presenta la información en tarjetas dentro de la interfaz.

#### CU-04 Seleccionar alojamiento

**Actor:** Usuario.

**Descripción:** permite seleccionar uno de los alojamientos mostrados para utilizarlo posteriormente en una reserva.

**Flujo principal:**

1. El usuario visualiza las opciones disponibles.
2. Selecciona un alojamiento.
3. La aplicación conserva el alojamiento seleccionado.
4. El formulario de reserva utiliza dicha selección para asociar la nueva reserva.

#### CU-05 Registrar reserva

**Actor:** Usuario.

**Descripción:** permite registrar una reserva para un alojamiento existente.

**Flujo principal:**

1. El usuario selecciona un alojamiento.
2. Ingresa su nombre y correo electrónico.
3. Selecciona las fechas de entrada y salida.
4. Indica el número de huéspedes.
5. El frontend valida los datos ingresados.
6. La información es enviada al backend.
7. El backend verifica que el alojamiento exista.
8. La reserva se almacena en la base de datos.
9. El sistema devuelve la confirmación con el identificador de la reserva.

#### CU-06 Gestionar alojamiento

**Actor:** Administrador del sistema.

**Descripción:** permite crear, consultar, modificar o eliminar alojamientos mediante los servicios expuestos por el backend.

#### CU-07 Gestionar reserva

**Actor:** Administrador del sistema.

**Descripción:** permite consultar, actualizar y eliminar reservas registradas utilizando los endpoints correspondientes de la API REST.

### 4.4 Historias de usuario

#### HU-01 Registro de usuario

**Como** usuario,  
**quiero** crear una cuenta utilizando mis credenciales,  
**para** poder identificarme dentro del sistema.

**Criterios de aceptación:**

- El sistema debe permitir registrar un nombre de usuario y una contraseña.
- La contraseña no debe almacenarse directamente en texto plano.
- El sistema debe informar si el registro fue exitoso.

#### HU-02 Inicio de sesión

**Como** usuario registrado,  
**quiero** iniciar sesión con mis credenciales,  
**para** comprobar que mi identidad puede ser validada por el sistema.

**Criterios de aceptación:**

- El sistema debe validar el nombre de usuario.
- El sistema debe comparar correctamente la contraseña ingresada.
- Una contraseña incorrecta debe producir un resultado de autenticación fallido.
- Las credenciales correctas deben producir un resultado satisfactorio.

#### HU-03 Consulta de alojamientos

**Como** visitante de la aplicación,  
**quiero** consultar los alojamientos registrados,  
**para** conocer las opciones disponibles.

**Criterios de aceptación:**

- La información debe provenir de la API REST.
- Cada alojamiento debe mostrar su nombre, descripción, capacidad y precio por noche.
- Los alojamientos deben ser mostrados mediante componentes reutilizables en React.

#### HU-04 Selección de alojamiento

**Como** usuario,  
**quiero** seleccionar un alojamiento,  
**para** utilizarlo al momento de registrar una reserva.

**Criterios de aceptación:**

- El usuario debe poder seleccionar una opción desde la interfaz.
- El alojamiento seleccionado debe conservar su identificador.
- La reserva debe quedar asociada al alojamiento elegido.

#### HU-05 Registro de reserva

**Como** usuario,  
**quiero** registrar una reserva indicando mis datos y fechas de estadía,  
**para** solicitar un alojamiento desde la aplicación.

**Criterios de aceptación:**

- Debe existir un alojamiento seleccionado.
- El nombre y el correo electrónico son obligatorios.
- La fecha de salida debe ser posterior a la fecha de entrada.
- El número de huéspedes no debe superar la capacidad del alojamiento.
- La reserva debe almacenarse mediante la API REST.
- La aplicación debe mostrar un mensaje de confirmación cuando la operación finalice correctamente.

## 5. Metodología de desarrollo, control de versiones y buenas prácticas

### 5.1 Metodología de desarrollo

Para el desarrollo e integración del sistema **Divina Providencia** se utilizó un enfoque incremental.

El proyecto fue construido por módulos independientes que posteriormente fueron integrados dentro de una única solución FullStack.

El proceso general de trabajo se organizó de la siguiente manera:

1. Identificación de los requerimientos funcionales del sistema.
2. Desarrollo inicial de los módulos de frontend y backend.
3. Organización de los componentes dentro de una estructura FullStack.
4. Integración del frontend React con la API REST de Spring Boot.
5. Configuración de la conexión con la base de datos MySQL.
6. Integración del módulo de alojamientos.
7. Integración del módulo de reservas.
8. Integración del módulo de autenticación.
9. Implementación y ejecución de pruebas unitarias.
10. Compilación de los componentes frontend y backend.
11. Control de versiones de los cambios mediante Git.
12. Documentación técnica del proceso de integración.

Este enfoque permitió comprobar el funcionamiento de cada módulo antes de continuar con el siguiente, reduciendo la posibilidad de introducir errores difíciles de identificar.

### 5.2 Estrategia de integración

La integración se realizó de manera progresiva.

Inicialmente se comprobó que el backend pudiera ejecutarse correctamente y acceder a la información almacenada en MySQL.

Posteriormente, el frontend fue configurado para consumir la API utilizando solicitudes HTTP.

La integración se realizó primero con el módulo de alojamientos, debido a que permitía comprobar de manera sencilla la comunicación entre React y Spring Boot.

Una vez validada esta comunicación, se integraron los módulos de reservas y autenticación.

Cada etapa fue comprobada individualmente antes de incorporarla al flujo general de la aplicación.

### 5.3 Control de versiones

El proyecto utiliza **Git** como sistema de control de versiones.

El control de versiones permite conservar un historial de los cambios realizados en el código fuente y facilita la identificación de las diferentes etapas de desarrollo del proyecto.

Durante la integración se realizaron commits asociados a funcionalidades específicas.

### 5.5 Buenas prácticas de desarrollo

Durante la implementación del proyecto se aplicaron diferentes prácticas orientadas a mantener el código organizado, comprensible y reutilizable.

#### Separación de responsabilidades

Cada parte del sistema tiene una función específica.

Por ejemplo:

```text id="jqrx4x"
Controller → recibe solicitudes HTTP

Service → ejecuta la lógica de negocio

Repository → accede a los datos

Model → representa las entidades

DTO → transporta información entre capas

React Component → representa partes de la interfaz

Frontend Service → comunica React con la API
```

Esta separación evita concentrar toda la lógica del sistema en un único archivo.

#### Componentes reutilizables

En el frontend se utilizan componentes de React independientes.

Por ejemplo, `AccommodationCard` puede utilizarse para representar diferentes alojamientos sin duplicar la estructura de la tarjeta.

De manera similar, los servicios del frontend centralizan las peticiones HTTP y evitan repetir la misma lógica de conexión en diferentes componentes.

#### Nombres descriptivos

Se utilizaron nombres relacionados directamente con la responsabilidad de cada clase, método o componente.

Algunos ejemplos son:

```text id="za3upp"
AccommodationService
ReservationService
AuthService
createReservation()
getAccommodations()
registerUser()
loginUser()
```

Esto facilita la lectura y mantenimiento del código.

#### Validación de datos

El formulario de reservas realiza validaciones antes de enviar la información al backend.

Entre ellas se encuentran:

- existencia de un alojamiento seleccionado;
- nombre obligatorio;
- correo electrónico válido;
- fechas de entrada y salida;
- validación del número de huéspedes;
- comparación con la capacidad máxima del alojamiento.

Estas validaciones ayudan a reducir solicitudes incorrectas hacia el backend.

#### Manejo de errores

Los servicios del frontend verifican las respuestas HTTP utilizando la propiedad `response.ok`.

Cuando una operación falla, se genera un mensaje que posteriormente puede mostrarse al usuario.

Esto permite diferenciar una respuesta correcta de una solicitud que presentó un problema.

## 6. Seguridad, configuración del servidor y base de datos

### 6.1 Mecanismos de seguridad implementados

El sistema **Divina Providencia** incorpora mecanismos básicos de seguridad orientados principalmente a la protección de credenciales, validación de solicitudes y control de la comunicación entre el frontend y el backend.

Para el alcance de esta evidencia se implementaron medidas relacionadas con el almacenamiento de contraseñas, validación de autenticación, configuración CORS y protección de archivos de configuración sensibles.

### 6.2 Protección de contraseñas

El módulo de autenticación utiliza un componente `PasswordEncoder` proporcionado mediante la configuración del backend.

La contraseña ingresada por el usuario no se almacena directamente en texto plano.

Durante el registro se realiza un proceso similar al siguiente:

```text id="q25b8u"
Contraseña ingresada
        ↓
PasswordEncoder
        ↓
Contraseña codificada
        ↓
Base de datos
```

Posteriormente, durante el inicio de sesión, el sistema no compara directamente dos textos. En su lugar utiliza el mecanismo de validación proporcionado por `PasswordEncoder`.

El flujo general es:

```text id="vk2hiw"
Usuario ingresa contraseña
          ↓
AuthService
          ↓
PasswordEncoder.matches(...)
          ↓
Comparación con el valor almacenado
          ↓
Autenticación válida o inválida
```

Esta implementación reduce el riesgo asociado al almacenamiento directo de contraseñas legibles dentro de la base de datos.

### 6.3 Validación de autenticación

La lógica del módulo de autenticación se encuentra centralizada en:

```text id="wch1o2"
AuthService
```

Entre las operaciones implementadas se encuentran:

```text id="buk339"
userExists(...)
register(...)
authenticate(...)
```

Antes de registrar un usuario se puede verificar la existencia del nombre de usuario.

Durante la autenticación, el sistema busca el usuario registrado y posteriormente valida la contraseña proporcionada.

Cuando el usuario no existe o la contraseña no coincide, la autenticación devuelve un resultado negativo.

Estas situaciones también fueron verificadas mediante pruebas unitarias.

### 7.9 Patrones y principios utilizados

La solución utiliza diferentes patrones y principios de organización.

#### Arquitectura por capas

El backend separa:

```text
Controller
    ↓
Service
    ↓
Repository
```

Cada capa tiene una responsabilidad definida.

#### Repository Pattern

Los repositorios encapsulan el acceso a los datos mediante Spring Data JPA.

Ejemplos:

```text
UserRepository
AccommodationRepository
ReservationRepository
```

De esta forma, los servicios no necesitan implementar directamente consultas JDBC para realizar las operaciones principales.

#### Service Layer

La lógica del negocio se concentra en clases de servicio:

```text
AuthService
AccommodationService
ReservationService
```

Esto evita incluir la lógica directamente dentro de los controladores.

#### Component-Based Architecture

React utiliza una arquitectura basada en componentes.

Elementos como:

```text
AccommodationCard
AuthSection
ReservationForm
```

pueden mantener responsabilidades independientes y ser reutilizados dentro de la aplicación.

#### Data Transfer Object

Se utilizan DTO para transportar información específica entre el cliente y el servidor.

Ejemplos:

```text
AuthRequest
AuthResponse
ReservationRequest
```

Esto permite separar la información utilizada por la API de las entidades internas de persistencia.
